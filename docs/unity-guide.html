01

Install Unity

Unity Hub manages editor versions, modules and licenses. Install the Hub first, then the editor through it.

  1. Download Unity Hub from unity.com/download and sign in with your Unity ID. On first launch, the Hub offers to activate a Personal license. Accept it.
  2. Install an editor: go to Installs → Install Editor and pick the newest Unity 6.3 LTS (6000.3.x, supported until December 2027).
    LTS or the newest release?Newer "Supported" releases such as 6.6 get updates until the next one ships. LTS versions get two years of fixes. Ship on LTS, and only move up when the next LTS (6.7, expected late 2026) has had a few patches.
  3. Tick these modules (you can add more later from the editor's gear menu):
    • Android Build Support, including OpenJDK and the Android SDK & NDK tools
    • iOS Build Support (only installable on a Mac)
    • Web Build Support (optional): lets you keep a browser build for quick playtests, like the prototype
    • Documentation (an offline manual, useful on planes)
  4. Pick a code editor: VS Code (free) with the Unity extension, JetBrains Rider (free for non-commercial use), or Visual Studio. In Unity, set it under Settings → External Tools. Claude Code works alongside any of them.
  5. Disk space: each editor plus its modules takes tens of GB. Keep projects on an SSD.
02

Set up the project

Create the project, then set it up to match the prototype, so the first drive feels familiar.

  1. New project → Universal 2D (URP with the 2D Renderer). Name it BumperBlock. If you'll use Unity services, tick Connect to Unity Cloud.
  2. Version-control-friendly settings: under Project Settings → Editor, set Asset Serialization = Force Text and make sure .meta files are visible (the default in Unity 6). Scenes and prefabs then become YAML that Git can diff and merge.
  3. Player settings: company name, product name Bumper Block, package name com.<you>.bumperblock. Set Default Orientation to Auto Rotation, with only Landscape Left and Landscape Right allowed. The prototype is landscape-only.
  4. Physics 2D, to start where the prototype ended:
    SettingPrototype valueWhere in Unity
    Gravity0, 0 (top-down)Project Settings → Physics 2D
    Step rate60 HzProject Settings → Time → Fixed Timestep = 0.0166667
    Solver iterationsvelocity 8, position 3Physics 2D → Velocity / Position Iterations
    Unitsmeters; car 1.8 × 1.0; arena 40 × 241 Unity unit = 1 m. Sprites: Pixels Per Unit to suit your art
    Damping, restitution, frictionsee config.jsRigidbody2D.linearDamping, a Physics Material 2D
  5. Input System: Unity 6 uses the new Input System by default. Make one Input Actions asset with Steer, Brake, Boost, Ability, Cycle and Select1–3, bound to touch (screen halves, buttons) and keyboard (A/D, S, Space, F, Q, 1/2/3). The keys match the prototype.
  6. Folder layout (one suggestion): 
    Assets/
  _Project/
    Scripts/      # Driving/ Matching/ Damage/ AI/ Abilities/ Weather/ UI/ Audio/
    Config/       # ScriptableObjects: the config.js values, one per system
    Prefabs/      # PlayerCar, Car, Motorcycle, Bus, Semi, Police, Junk
    Scenes/       # Boot, Game, (Menu)
    Art/ Audio/ Fonts/
  Plugins/        # third-party SDKs
Tests/
  EditMode/ PlayMode/   # Unity Test Framework: ports of tests/*.test.mjs
For Bumper Block: turn config.js into ScriptableObjectsMake one asset per system (DrivingConfig, MatchConfig, DamageConfig, WeatherPreset…), filled with the prototype's values. Designers can then tune in the Inspector, and later the same fields can be overridden remotely (see A/B tests).
03

Hooking up GitHub

Yes, this works. Unity Hub has no "connect GitHub" button, so you use Git directly (or GitHub Desktop) and set up three files.

Recommended

Git + GitHub

Works with Claude Code everywhere, including cloud sessions like the ones that built the prototype. GitHub Actions can build and test the game. Large binaries go through Git LFS.

Alternative

Unity Version Control (Plastic)

Built for big binary assets, with file locking for artists. Since March 2026 there's no per-seat charge for cloud hosting, and the first 100 GB a month is free. It's less convenient with Claude Code and GitHub-based tooling.

  1. Create the repo on GitHub (bumperblock-unity, private). Initialize it without a README so the first push is clean.
  2. Add a .gitignore at the project root (the folder that contains Assets/). Start from GitHub's maintained template: github/gitignore → Unity.gitignore. It ignores Library/, Temp/, Obj/, Logs/, UserSettings/, Build*/ and IDE files.
  3. Add .gitattributes for LFS and Unity's merge tool: 
    # Unity YAML: merge with UnityYAMLMerge (SmartMerge)
*.unity  merge=unityyamlmerge eol=lf
*.prefab merge=unityyamlmerge eol=lf
*.asset  merge=unityyamlmerge eol=lf
*.mat    merge=unityyamlmerge eol=lf
*.anim   merge=unityyamlmerge eol=lf
# Big binaries: Git LFS
*.png  filter=lfs diff=lfs merge=lfs -text
*.psd  filter=lfs diff=lfs merge=lfs -text
*.wav  filter=lfs diff=lfs merge=lfs -text
*.ogg  filter=lfs diff=lfs merge=lfs -text
*.mp3  filter=lfs diff=lfs merge=lfs -text
*.ttf  filter=lfs diff=lfs merge=lfs -text
*.fbx  filter=lfs diff=lfs merge=lfs -text
  4. Register the merge tool once per machine. UnityYAMLMerge ships inside the editor's Data/Tools folder, so adjust the path to your install: 
    git config --global merge.unityyamlmerge.name "Unity SmartMerge"
git config --global merge.unityyamlmerge.driver \
  '"/Applications/Unity/Hub/Editor/6000.3.x/Unity.app/Contents/Tools/UnityYAMLMerge" merge -p %O %B %A %A'
  5. First commit and push: 
    cd BumperBlock
git init -b main
git lfs install
git add .gitignore .gitattributes
git add .
git commit -m "Empty Universal 2D project"
git remote add origin https://github.com/<you>/bumperblock-unity.git
git push -u origin main
  6. CI (optional, recommended): GameCI provides GitHub Actions (game-ci/unity-test-runner, game-ci/unity-builder) that run your tests and build Android/Web on every push. Follow its Activation guide; Personal and Pro licenses are set up differently. The Unity-native option is Unity Build Automation, which connects to the GitHub repo. Its free monthly allowance is about 200 Windows minutes and 100 Mac minutes, and it can make iOS builds without your own Mac.
Scenes and mergesEven with SmartMerge, two people (or two Claude sessions) editing the same scene will collide. Keep scenes thin: build the game from prefabs and code, and spawn things at runtime the way the prototype does.
04

Hooking up Claude Code

There are three levels of connection. Each is useful on its own, and you can stack them.

How the pieces connect. Code goes up through GitHub, builds go out to the stores, and live services talk to the running game.

Level 1: Claude Code in the project folder

This works on day one, with nothing Unity-specific installed. Claude reads and writes C#, Unity recompiles when you switch back to the editor, and Claude can run tests from the command line.

# macOS / Linux / WSL
curl -fsSL https://claude.ai/install.sh | bash
# Windows PowerShell
irm https://claude.ai/install.ps1 | iex

cd BumperBlock
claude            # then type /init to generate a CLAUDE.md

Give it the prototype as reference by cloning it next to the project. Read-only is fine:

git clone https://github.com/ventiduke/bumperblock.git ../bumperblock-prototype

Then make CLAUDE.md point at it. A starting version:

# Bumper Block (Unity)
Unity 6.3 LTS, URP 2D, C#. Port of the web prototype at ../bumperblock-prototype
(live: https://ventiduke.github.io/bumperblock/).

- Read ../bumperblock-prototype/docs/unity-handoff.md before changing gameplay.
  Keep each system's *intent*; the prototype's mechanism and numbers are a baseline, not a spec.
- Tuning lives in ScriptableObjects under Assets/_Project/Config (ported from config.js).
  Never hard-code a tuning number in a script.
- Physics: Rigidbody2D, gravity 0, Fixed Timestep 1/60. Per-step forces in FixedUpdate only.
- Tests: Unity Test Framework in Tests/. Port the matching tests/*.test.mjs checks
  when you port a system. Run:
  Unity -batchmode -projectPath . -runTests -testPlatform PlayMode -testResults results.xml
- Keep scenes thin; spawn from prefabs in code to avoid scene merge conflicts.

Level 2: Unity's official plugin for Claude Code

Unity publishes a Claude Code plugin with Unity-written skills (engine know-how) plus support for the Unity CLI, so Claude can drive the editor: create objects, run builds, read the console. Install it from inside a Claude Code session:

/plugin marketplace add Unity-Technologies/unity-agent-plugin
/plugin install unity@unity-agent-plugin

The skills that control the editor need three things: the Unity CLI installed, the Pipeline package in the project (unity pipeline install), and the editor open. Unity's AI pieces are moving quickly, so follow Unity's plugin page for the current steps.

Level 3: Unity MCP (live editor access)

An MCP server gives Claude live access to the open project: scenes, GameObjects, console output and build settings.

Official

Unity MCP (AI Assistant package)

Needs Unity 6+, a project connected to Unity Cloud, and access to Unity's AI tools (a trial or subscription). Set it up from the AI Assistant's Integrations panel, which can configure Claude Code for you. Unity is moving MCP features into the Unity CLI, so check which route is current.

Community, free

Open-source MCP servers

For example CoplayDev/unity-mcp, CoderGamester/mcp-unity and IvanMurzak/Unity-MCP. They're no-cost, and quality varies. Read the code before you give one access to your editor.

Cloud vs. localClaude Code on the web (like the sessions that built the prototype) is great for C# changes, tests that run in batch mode on CI, docs and reviews. It can't open the Unity Editor. Anything visual, such as scenes, feel, or play mode, happens locally on your machine.

Prompts that work well for a port

  • "Port js/physics.js and js/player.js to a CarController MonoBehaviour plus a DrivingConfig ScriptableObject. Match the grip/drive/steer model in the handoff §3.1, and port the brake and reverse checks from tests/core.test.mjs as PlayMode tests."
  • "Compare our MatchSystem against js/match.js: list every behavior in the prototype that we don't have yet."
  • "Write an editor window that shows the live values of the current level's configs, like the prototype's ?debug=1 overlay."

Port the prototype: feel first

Build in the order the playtests did: driving, then the crowd, then matching, then pressure. Don't move to the next milestone until the current one feels like the web build, played side by side on the same phone.

M1
Driving feelphysics.js, player.js → CarController: capped lateral grip, forward drive, near-direct angular velocity, brake and reverse, boost. Camera follow with look-ahead.
M2
Crowd and collisionsai.js, spawner.js → wander, wall avoidance, stun on hard hits, spawning from the edges. The "weighty bumps" feel (§3.2).
M3
Chain matchingmatch.js, effects.js → trigger colliders, union-find, player as a wildcard link, countdown, explosion shove, particles.
M4
Pressuredamage.js, pileup.js, stuck detection → fault-based damage, squeeze, repair windows, rust and junk, boxed-in.
M5
Levels and HUDlevels.js, hud.js → goals, stars, results screen, toasts, minimap (a second camera or a RenderTexture).
M6
Vehicles and policeMotorcycle, bus, semi (HingeJoint2D), police chase and ram with skid, convoy bonus.
M7
Abilities and upgradesabilities.js, upgrades.js → chameleon, phase (layer matrix), tow (DistanceJoint2D), the card draft, run summary.
M8
Terrain and weatherterrain.js, weather.js → surface zones, puddles, wind drift, lightning. Visuals become particle systems and 2D lights.
M9
Sound and feelaudio.js → real sound design (an AudioMixer and snapshots), hitstop, skid marks, haptics (now iOS too).

Getting assets

Start with placeholders that read well (the prototype's flat shapes are a fine start), then upgrade in passes. Keep a record of every asset's license from day one.

Art

Sprites and VFX

  • Unity Asset Store: buy it, then it's in Package Manager → My Assets
  • Kenney: CC0 top-down car and racing packs, ideal for a first pass
  • itch.io game assets
  • A commissioned artist for the final look and player car skins
Audio

SFX and music

  • Kenney audio packs (CC0)
  • Freesound: licenses vary per sound, so check each one
  • The prototype's synth sounds work as a spec: each event and how it should feel
  • Horns and engine sounds per vehicle type from a sound library or a sound designer
Type and UI

Fonts and UI kits

  • Google Fonts (mostly OFL, safe to embed)
  • Unity UI Toolkit or uGUI. Build the HUD to scale with the screen and respect safe areas (notches).
License hygieneAdd CREDITS.md to the repo, with each asset's source, author, license and URL. Store reviews and publishers ask for this. If you use AI-generated art or audio, check the tool's commercial terms and each store's current disclosure rules.
For Bumper Block: readability firstSix colors, five vehicle types, junk and weather all share one phone screen. Give each color a shape or pattern as well (colorblind support), keep sprites top-down and high-contrast, and test every art pass at night and in fog, where readability suffers most.
07

Publishing basics (Unity-native first)

Unity 6 manages platforms with Build Profiles (File → Build Profiles). Make one per platform, plus a "Dev" profile with development build and profiler on.

Android

Google Play

  1. Build Profiles → Android → Switch Platform.
  2. Player Settings: IL2CPP, ARM64. Target API level must be 36 (Android 16) or higher for new apps and updates since Aug 31, 2026.
  3. Create a keystore in Publishing Settings. Back it up somewhere safe; with Play App Signing, Google holds the release key.
  4. Tick Build App Bundle (AAB) and build.
  5. Play Console: create the app, then fill in the store listing, content rating (IARC), Data safety form, privacy policy URL, and target audience.
  6. Upload to Internal testing, then closed testing (required for new personal accounts), then production.
iOS

App Store

  1. Build Profiles → iOS. Unity exports an Xcode project.
  2. Open it in Xcode 26+ (required for uploads since Apr 28, 2026), and set signing to your team.
  3. Product → Archive, then upload to App Store Connect.
  4. Test with TestFlight (internal testers right away; external testers after a light review).
  5. Fill in the App Privacy "nutrition labels", age rating and screenshots, then submit for review.
  6. No Mac? Unity Build Automation can build and sign in the cloud. You still need the Apple Developer account and certificates.
Web

Keep a browser build

A Web build profile gives playtesters a link, like the prototype's GitHub Pages. Host it on itch.io (free, with a password option) or Pages. Mobile browsers are a weaker target for Unity than native, so use it for desktop playtests.

Automation

Unity Build Automation

Connects to your GitHub repo, builds on push, and can deliver to TestFlight and Play. It's Unity's native answer to CI for builds, and pairs with GameCI for tests on GitHub Actions.

Release hygieneBump Version (shown to players) and Bundle Version Code / Build (must always increase) on every upload. Tag releases in Git, which gives you the prototype-v1 habit for free.

Advanced: ads

After the game is fun

Unity's ad stack is now LevelPlay, its mediation platform. As of Jan 31, 2026, Unity Ads no longer supports direct SDK integration through the old Advertisement Legacy package. Unity Ads runs through LevelPlay, with in-app bidding.

  1. Install Ads Mediation (LevelPlay) from the Package Manager, and create the app in the LevelPlay dashboard.
  2. Add networks under Mediation → Setup → SDK Networks, starting with Unity Ads. The auto-setup tool creates the placements.
  3. Integrate one ad format at a time. Start with rewarded.
  4. Handle consent before showing ads: GDPR/UMP in Europe, App Tracking Transparency on iOS, and COPPA if children might play.

Advanced: A/B tests and bandit-style tuning

This is where turning config.js into ScriptableObjects pays off. Expose the numbers you're unsure about as remote keys, then let real players decide.

The plumbing (Unity-native)

  1. Remote Config: key/value settings fetched at startup and cached, with your ScriptableObject value as the fallback. Example keys: police_cap_level3, repair_on_time, snow_grip, interstitial_every.
  2. Game Overrides: server-side rules that change Remote Config values for an audience, with a built-in A/B test that splits players into variants. No extra SDK; it's configured in the Dashboard (or as code with the Deployment package).
  3. Analytics: send the events that decide the test (below), and compare variants in the Dashboard.
// Sketch: apply remote values over the ScriptableObject defaults at boot.
await UnityServices.InitializeAsync();
await AuthenticationService.Instance.SignInAnonymouslyAsync();
await RemoteConfigService.Instance.FetchConfigsAsync(new UserAttributes(), new AppAttributes());
var rc = RemoteConfigService.Instance.appConfig;
damage.repairOnTime   = rc.GetFloat("repair_on_time", damage.repairOnTime);
levels[2].policeCap   = rc.GetInt("police_cap_level3", levels[2].policeCap);
weather.snow.grip     = rc.GetFloat("snow_grip", weather.snow.grip);

What to measure

The prototype's run summary is already the right event list:

  • level_start and level_complete (time, stars, health left)
  • level_fail (wrecked or boxed in, plus the top damage source)
  • card_picked
  • ability_used
  • ad_watched
  • purchase
  • session length and D1/D7 retention

Pick one primary metric per test (e.g. "level 3 completion rate" or "D7 retention") before you start it.

A/B test or bandit?

A/B test

"Is B better than A?"

Fixed split, run to a planned sample size, then decide. Best for decisions you'll live with: does the police cap on level 3 hurt completion? Does an interstitial every 2 levels hurt D7?

Multi-armed bandit

"Keep finding the best value"

Traffic shifts toward the variants that are winning while the test runs, so fewer players get a bad experience. Best for ongoing tuning with several candidate values: repair window length, ad frequency, a starting-health curve.

Ways to run a bandit

  • Firebase Remote Config Personalization (off the shelf). It uses a contextual multi-armed bandit to pick, for each player, one of up to five alternative values, optimizing a Google Analytics event you choose. It works with the Firebase Unity SDK and can run alongside Unity services.
  • Do it yourself on Unity Gaming Services:
    • Store a success and failure count per arm (Cloud Save, or your own small backend).
    • A Cloud Code function picks each player's arm by Thompson sampling.
    • The game reports the outcome back.
    More work, full control: 
    // Thompson sampling: draw from each arm's Beta(successes+1, failures+1); serve the highest draw.
int PickArm(Arm[] arms) {
  int best = 0; double bestDraw = -1;
  for (int i = 0; i < arms.Length; i++) {
    double draw = SampleBeta(arms[i].wins + 1, arms[i].losses + 1);
    if (draw > bestDraw) { bestDraw = draw; best = i; }
  }
  return best;  // assign once per player (sticky), report win/loss at level end
}
Guardrails
  • Keep each player's assignment sticky (same variant every session).
  • Bound every arm to values you'd be happy to ship.
  • Never optimize monetization alone. Watch retention alongside it.
  • Don't change gameplay values in the middle of a run.
  • Before going live, run candidate values through the bot simulations to screen out broken ones.

Advanced: in-game store and purchases

Use Unity IAP (the In-App Purchasing package, v5.x; 5.4.4 when this was checked) for the store-facing part, and Economy (UGS) if you want virtual currency and inventory on a server.

  1. Design the catalog first. Cosmetics suit this game: player car skins, horn sounds, explosion colors, skid-mark trails. Add "Remove ads", and a small starter pack if you have a soft currency. Keep anything that affects gameplay out of the paid store, to protect the balance you tuned.
  2. Set up products in each store: Play Console → Monetize → Products, and App Store Connect → In-App Purchases. Use the same product IDs on both, e.g. bb.removeads, bb.skin.chrome. On Apple, the Paid Apps agreement, tax and banking forms must be complete first.
  3. Integrate IAP v5: v5 reworked the connection and purchase flow, and Unity provides AI skills for migrating from v4. From v5.4, you manage player consent with the UnityConsent module.
  4. Validate receipts on a server (Unity's validation, or Cloud Code) before granting anything valuable. Add a Restore Purchases button; Apple requires it for non-consumables.
  5. Economy (optional): currencies such as coins earned from levels, inventory items (owned skins) and virtual purchases, all held server-side so they can't be edited on the device. Store prices can be A/B tested with Game Overrides.
  6. Test with sandbox and license-tester accounts on both stores before review. Purchase flows are the most common cause of review rejections.

Anything else you missed? A few things

These aren't in your list, but they're needed before launch or hard to add later.

Analytics and crash reporting

Wire in Unity Analytics events at M5 (levels), not at launch, so playtest data starts early. Add crash and exception reporting (Unity's diagnostics, or Firebase Crashlytics).

Saves and accounts

Save progress locally first. Then add Unity Authentication (anonymous sign-in, later linked to Apple/Google) plus Cloud Save, so a new phone doesn't lose skins and progress.

Onboarding

Your next priority. Teach one mechanic per level: steer, chain-match, the repair color, junk, abilities, cops, weather. Use contextual prompts the first time each thing happens, and record which hints get skipped.

Difficulty and progression

Level and difficulty data in ScriptableObjects, tuned against real-player analytics, not bots. Build the persistent skill tree from the cards people actually pick.

Accessibility

Color plus shape coding, scalable HUD text, and toggles for haptics, camera shake and flashing. Lightning flashes need a "reduce flashing" option for photosensitive players.

Performance on cheap phones

Profile on a low-end Android early. Use pooling for cars and particles, sprite atlases, a 60 fps target and a battery check. The prototype's "60 cars at 60 fps" is the bar.

Privacy, legal, business

A privacy policy and terms (hosted URL), age rating, store data-safety and privacy labels, and ATT. A trademark search on "Bumper Block". Decide whether to publish as an individual or a company, and set up tax and banking.

Localization

Unity's Localization package. Keep every string out of code from the start, even if you only ship English.

Store presence (ASO)

Icon, a short gameplay trailer (the explosions and lightning are your hook), screenshots per device size, and a description with keywords. Plan to test icons too: Play Console has store listing experiments.

Soft launch and live ops

Launch in one or two smaller markets first and watch D1/D7 retention, session length and level funnels before going worldwide. Plan a cadence of new arenas, weather and skins.

Community and feedback

A Discord or subreddit, an in-game feedback link, and a TestFlight/Play testing group you can call on, so you're not limited to one tester.

Keep the prototype alive

It's the fastest place to try a wild idea (a new ability, a new weather type) in an afternoon before spending a week on it in Unity.
